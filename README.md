# Merkledrop

**Airdrop tokens to thousands of Stellar addresses for the cost of one hash.**

Pushing an airdrop one payment at a time is slow and expensive, and it
fails for anyone who hasn't set up a trustline. Merkledrop flips it
around:

1. **You** put the allocation list into a Merkle tree (`tools/`), deploy
   the contract with the tree's 32-byte **root**, and fund it once.
2. **Each recipient** claims their own tokens with a short proof (about
   `log₂(n)` hashes, so 9 for 257 recipients and 20 for a million).
3. After the claim window, you **sweep** whatever is unclaimed back.

The contract stores one hash plus one bit per claim. The full list
lives off-chain (publish it anywhere) and nobody can claim an amount
that isn't in it.

## Tools: build the tree

```bash
cd tools && npm install && npm run build
cat allocations.csv
# address,amount
# GBRPYHIL2CI3FNQ4BXLFMNDLFJUNPU2HY3ZMFSHONUCEOASW7QC7OX2H,10000000000
# GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN,2500000000
node dist/bin.js allocations.csv drop.json
# root:   cc35b45e…
# total:  12500000000 (fund the contract with at least this)
# claims: 2 → drop.json
```

`drop.json` holds every recipient's `{ index, account, amount, proof }`.
Serve it from your claim page so each user can find their entry.
Amounts are whole numbers in the token's base unit (1 XLM = 10,000,000).
Duplicate addresses and invalid keys are rejected.

## Contract

| Function | Who signs | Notes |
| --- | --- | --- |
| `init(admin, token, root, funding, ends_at)` | admin | Pulls `funding` from the admin, once |
| `claim(index, account, amount, proof)` | anyone | Tokens always go to `account`, so a relayer can pay the fee |
| `verify(index, account, amount, proof)` | anyone | Check a proof without claiming |
| `sweep()` | admin | After `ends_at`; returns the remainder |
| `is_claimed(index)`, `get_drop()` | anyone | Read state |

Errors: `AlreadyInitialized (1)`, `NotInitialized (2)`, `AlreadyClaimed (3)`,
`InvalidProof (4)`, `Ended (5)`, `NotEnded (6)`, `InvalidAmount (7)`,
`InvalidEnd (8)`.

### Hashing (identical in Rust and TypeScript)

```text
leaf = sha256( index:u32 big-endian ‖ amount:i128 big-endian ‖ address as ScVal XDR )
node = sha256( min(a, b) ‖ max(a, b) )
```

Including the index makes each leaf unique and lets the contract track
claims with one flag per index. Sorted pairs mean proofs need no
left/right markers. The contract's tests embed a root and proofs
generated by the TypeScript builder, for both G-accounts and contract
addresses, so any drift between the two implementations fails CI.

## Glossary (new to Stellar?)

- **Airdrop**: distributing tokens to many addresses at once.
- **Merkle tree / root**: a way to fingerprint a whole list with one hash.
  Change any entry and the root changes.
- **Merkle proof**: the few sibling hashes needed to show one entry is
  in the list, without revealing or storing the rest.
- **Trustline**: a classic Stellar account's opt-in to hold an asset. A
  claim-based drop lets users set one up first, then claim.
- **Sweep**: return unclaimed tokens after the deadline.
- **ScVal XDR**: Soroban's canonical binary encoding of a value, used
  here so both implementations hash addresses identically.
